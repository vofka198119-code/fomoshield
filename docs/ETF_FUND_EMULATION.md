# Эмуляция фондов (ETF) — FOMO Shield Fund Market

Статус: обсуждение концепции, реализация не начата. Кода нет и не будет, пока экономическая модель не зафиксирована целиком.

## 0. Суть

Внутри FOMO Shield появляется виртуальная биржа инвестиционных фондов:
пользователь создаёт фонд → фонд проходит виртуальное IPO → другие пользователи покупают units фонда →
капитал фонда (AUM) растёт → команда управляющих принимает решения по составу активов →
единый мировой симулятор двигает цены → NAV фонда меняется → инвесторы видят P&L →
фонды соревнуются между собой по доходности/AUM/популярности.

Это отдельный большой модуль поверх текущего Stress Test Engine, а не расширение существующей фичи.

---

## 1. Создание фонда

Форма регистрации: Fund Name, Ticker, Logo, Description, Investment Strategy,
Starting Capital, Dividend Policy, Fund Manager, Co-Managers, Fund Rules.

## 2. Ограничение через Premium

Создание фонда доступно только по подписке (Premium 6 months / Premium+).
Работает как монетизация и как антиспам-фильтр (мешает штамповать мусорные фонды).

## 3. IPO / Approval

Submit for Listing → Pending Approval (админ / бот / комбинация) → Approved → попадает в New Funds.

## 4. Раздел FUNDS (биржа фондов)

Списки: Popular, Top by Capitalization, Top Gainers, Top Losers, Most Bought, Most Sold,
New Funds, Highest Dividend, Best Stress Resistance.

## 5. Buy / Sell — механика через units и NAV

Инвестор не покупает «акцию компании», а покупает **Fund Units**.

```
NAV = (рыночная стоимость активов фонда + cash) / units outstanding

Buy:  units_issued = amount / NAV_текущий;  AUM += amount;  units_outstanding += units_issued
Sell: payout = units_redeemed × NAV_текущий; AUM -= payout;  units_outstanding -= units_redeemed
```

Пример: AUM 100 000 / 10 000 units → NAV 10.00. Покупка 1000 → +100 units, AUM 101 000.
Рост активов на 10% → AUM 110 000 → NAV 11.00 → позиция инвестора 100×11 = 1100.

Деньги идут **в фонд, не управляющему напрямую** (Investor → Fund → Managers, не Investor → Manager).

## 6. Экономика управляющих

Два разных механизма, названы в исходном тексте вперемешку — см. открытый вопрос №2:
- **Ownership %** — управляющий держит units наравне с инвесторами (стартовый пакет при основании).
- **Management Fee** (например 1%/год) — периодическое списание с AUM в пользу управляющего.

## 7. Holdings и Activity

Текущий состав фонда (таблица Asset/Weight) отдельно от журнала действий (Bought/Sold/Added).

## 8. Management Room — управление фондом

Закрытый чат управляющих, Proposal → Approve/Reject → Decision approved → команда движку изменить allocation.
Связывает социальный слой с симуляцией.

## 9. Архитектура движков

```
Core Market Engine (единый мир: market phase, drift, sector/company behaviour, news, volatility, macro)
        ↓
Portfolio Engine (существующие пользовательские портфели — НЕ трогаем)
        ↓
Fund Engine (новое: AUM, NAV, units, subscriptions/redemptions, holdings, allocations, dividends, fees)
        ↓
Investor Engine (units держателя, средняя цена, P&L, dividends, exposure)
```

Один мировой рынок: у AAPL/MSFT/KO одна цена для всех фондов; разница в результатах — только
из-за разного состава портфеля. Существующий Stress Test Engine не ломаем, строим рядом.

## 10. Живая динамика фонда

AUM, NAV, число инвесторов/менеджеров, holdings, dividend yield меняются от net inflow/outflow.
Popularity/Trending — функция от притока капитала, доходности, стабильности, активности менеджеров,
дивидендов, возраста фонда, стрессоустойчивости. Создаёт петлю: хороший фонд → больше инвесторов →
больше AUM → выше в рейтинге → ещё больше инвесторов (и симметрично в обратную сторону).

## Разворот (2026-09-05): тренажёр для будущих финансовых аналитиков

Идея сохраняется, но меняется рамка: не «виртуальная биржа фондов с рейтингами и трендингом»,
а **обучающий тренажёр** для тех, кто реально учится на финансового аналитика. Это резонно снимает
конфликт с миссией приложения (антидот к FOMO), который был отмечен как открытый вопрос при первом
обсуждении — соревновательный фонд-маркет с Trending/Popularity сам провоцирует FOMO-поведение,
тренажёр для обучения — нет.

Что это меняет в уже описанной модели (разделы 1–10 выше, механика NAV/units не меняется):

- **Критерий успеха — не только P&L.** У аналитика оценивают качество обоснования решения, а не
  «угадал рост или нет». Management Room (раздел 8, Proposal → Approve/Reject) становится центральным
  учебным циклом (тезис → аргументация → факт-проверка результата), а не социальной надстройкой.
- **Рейтинги фондов (раздел 4, Trending/Popularity) теряют смысл** как виральность/AUM-гонка. Нужен
  другой критерий: точность прогноза, качество риск-менеджмента, сравнение с бенчмарком — предмет
  отдельного обсуждения.
- **Вопрос №3 (реальные деньги через Premium) упрощается** — вероятно, доступ к режиму разовый
  (Premium открывает тренажёр), а не экономика с fee, снятой с чужого реального AUM.
- **Вопрос №7 (anti-abuse/rug-pull) теряет остроту**, если в системе не крутятся деньги живых
  инвесторов-третьих лиц.
- **Новый вопрос:** кто и как оценивает качество решения аналитика — движок (сверка с реальным
  исходом через N дней), peer-review других учащихся, или заранее заготовленные кейсы с эталонным
  разбором? Это отдельная нетривиальная часть модели, которой не было в исходной версии.

---

## Решение (2026-09-05): реальный мульти-инвесторный маркетплейс, без вердикта

Вердикт/оценка качества решений полностью убирается из механики. Остаётся только отслеживание
баланса (AUM/NAV/units) созданных фондов. Подтверждено: это **реальный мульти-инвесторный
маркетплейс** — другие пользователи по-настоящему вкладывают (виртуальные) деньги в чужие фонды,
не соло-песочница. Это делает NAV/units экономически обязательной механикой (не декоративной), и
обостряет, а не снимает вопросы №1 (источник цен) и №8 (источник капитала) — там теперь реальные
интересы живых пользователей.

## План v1 (моё предложение, открыто для спора)

1. **Цены — реальный рынок**, не отдельный синтетический персистентный мир. Переиспользуем
   существующий live-фид (Finnhub/Yahoo), которым уже пользуется Portfolio. Синтетический мир —
   отдельный по трудозатратам проект и менее ценен для тренажёра аналитика, чем практика на
   настоящих ценах. Stress Test с управляемыми сценариями (crash/bull) остаётся отдельной фичей,
   не дублируется.
2. **Капитал — третий изолированный пул**, по уже устоявшемуся в приложении паттерну отдельных
   sandboxed-балансов по тирам (как у Portfolio $7k/$10k и Stress Test $7k/$15k). Fund Investing
   получает свой такой же баланс/слоты — не эмиссия из воздуха, не смешивание с балансом Portfolio.
3. **Management fee — отложено на v2.** В v1 вознаграждение управляющих — только founder units
   (бесплатная доля паёв при создании фонда), без периодического fee/минтинга/размытия.
4. **Ликвидность при Sell — всегда мгновенно по текущему NAV**, без искусственного дефицита кэша
   или slippage при распродаже активов.
5. **Governance v1 (пересмотрено 2026-09-05) — единоличное решение главы, не голосование.**
   Глава задаёт план ребаланса → аналитик формирует конкретный лимитный/рыночный ордер с
   обоснованием, виден в чате → глава подтверждает/просит поправить/отклоняет → только по
   подтверждению ордер уходит в исполнение. Никакого голосования между аналитиками — это надёжнее
   закрывает self-dealing, чем вариант с большинством голосов (сговор нескольких аналитиков там всё
   ещё возможен, здесь — нет, т.к. решает один ответственный человек).
6. **Жёсткий anti-abuse guardrail с первого дня:** управляющий(-ие) фонда не может инвестировать
   в свой же фонд. Это правило, а не опция — иначе self-dealing/wash trading становится тривиальным
   в первый же день после запуска.
7. **IPO-approval убран для v1.** Фонд публикуется сразу при создании (Premium уже фильтрует спам);
   модерация — постфактум (жалобы/ревью), не pre-approval очередь. Под вопросом: если очередь важна
   педагогически (студент учится защищать фонд перед «комиссией») — можно вернуть отдельным слоем.
8. **Trending/Popularity остаются как нейтральная статистика** (AUM, доходность, приток капитала),
   не как оценка качества — совместимо с отказом от вердикта.

Отложено на v2 явно: management fee, взвешенное голосование, возможный IPO-approval слой.

## Уточнение ролей и потока решений (2026-09-05)

- **Глава фонда** — создатель, стартовый капитал (например 200K), регистрирует фонд → фонд виден в
  поиске/новых разделах. Финальное решение всегда за ним.
- **Аналитики (сотрудники)** — нанимаются в закрытую команду фонда («офис-чат», приём в группу —
  отдельный процесс). Предлагают в чате ребаланс на плановую дату: конкретный актив, тип ордера
  (например лимитный), цену, аргументацию.
- **Поток утверждения:** аналитик предлагает → глава смотрит, просит поправить / отклоняет /
  утверждает → по утверждению жмёт кнопку → ордер уходит в исполнение по реальным котировкам.
- **Трек-рекорд аналитика:** каждый исполненный (утверждённый главой) ордер засчитывается в профиль
  аналитика как опыт/послужной список — межфондовый,Viewable resume-историей (работал в Фонде X,
  N предложений, M исполнено). **Важно держать это ledger-ом активности, а не скрытым вердиктом** —
  иначе это тихо возвращает механику оценки качества решений, которую договорились убрать. Стоит явно
  решить: это только счётчик участия/стажа, или туда же со временем попадёт качество исхода сделки?
- **Смена фонда аналитиком, видимая главе** — открытый вопрос, автор явно пометил как «нужно подумать»,
  не решаем сейчас.
- **Обычные инвесторы** — только покупка/продажа паёв фонда (как в реальности), НИКАКОГО влияния на
  внутренние решения фонда.
- **Bootstrapping ликвидности ботами:** пока в приложении мало живых пользователей, часть покупок/
  выводов из фондов будут делать бот-инвесторы (автоматически). Практически необходимо, но stoit решить
  прозрачность: должен ли создатель/пользователи фонда знать, что часть AUM/притока — синтетическая
  (боты), особенно раз это позиционируется как тренажёр для будущих аналитиков, где реалистичность
  сигнала имеет обучающую ценность. Риск — надутые метрики токсично подрывают доверие к фиче, если
  вскроется, что топ фонды росли на ботах, а не на реальном интересе.
- **Цены — подтверждено:** реальные котировки (тот же фид, что у Portfolio), НЕ движок Stress Test.
  Совпадает с предложенным в плане v1 пунктом 1.
- **Движок фонда — полностью серверный,** отдельная большая система. Автор пометил это как самую
  сложную часть — обсуждение продолжается.

## Уточнения, раунд 2 (2026-09-05)

- **Стартовый капитал фонда:** до 500K (лимит/потолок при создании). Открытая деталь: это фиксированный
  потолок для всех, или масштабируется по Premium-тиру (как у Portfolio/Stress Test)?

- **Anti-abuse, добавлено:** помимо запрета инвестировать в свой же фонд — фильтр контента чата

- **Трек-рекорд аналитика:** согласовано, что это должно быть похоже на «резюме аналитика» —
  конкретный дизайн (только счётчик активности или тоже что-то про качество) ещё не продуман,

- **Реестр держателей:** глава фонда видит полный список всех, кто владеет долей в фонде (кэп-таблица).

## Технический вызов: общее (не per-user) состояние фонда (2026-09-05)

Ключевое отличие от Stress Test: там у каждого пользователя своя изолированная симуляция, здесь —
все должны видеть **одно и то же** состояние фонда одновременно (цену, тики реальных компаний,
вклад холдингов в стоимость). Значит NAV не может считаться на клиенте — нужен единый серверный
источник истины.

**Предложенный подход:**
- **NAV считается по запросу (on-demand), не тикает постоянно фоновым процессом.** При открытии
  фонда или при сделке сервер берёт текущие цены холдингов через уже существующий прокси/рейт-лимитер
  Finnhub (тот же, что у Portfolio) и пересчитывает NAV = Σ(holding × цена) / units. Не нужен отдельный
  вечно работающий тикающий движок — дёшево и переиспользует существующую инфраструктуру.
- **Периодические снепшоты NAV** (например раз в день) — отдельный лёгкий фоновый job только для
  истории/графика, не для расчёта текущей цены.
- **Performance attribution** — вклад каждого холдинга в изменение NAV за период (например «AAPL дал
  +0.3% к NAV за день») — реальный навык аналитика, хорошо ложится в обучающую рамку, стоит держать
  в фиче-листе.
- **Сущности (концептуально, без схемы):** Fund, FundHolding (текущий состав), FundTransaction
  (журнал сделок/предложений), FundNavSnapshot (история для графика), FundInvestorPosition
  (паи по инвестору), FundTeamMember (роли: глава/аналитик).

## UI-референс (2026-09-05) — только концепция, не оформление

Пользователь прислал мокапы экранов, сгенерированные ChatGPT (Management Office чат, Proposal
voting, Hire Employee, Funds Market, Fund Details, Holdings, Fund Chart, Management Room, My
Investments). **Явно оговорено: берём только концепцию элементов, оформление строго в стиле
приложения**, финальный визуал будет правиться по месту при реализации.

Полезные концепты для заимствования:
- **Hire Employee с ролевой структурой:** Analyst / Co-Manager / Trader / Risk Manager / Research
  Assistant — расширяет плоское «аналитик» до полноценного офиса ролей. Увеличивает scope, решать
  при переходе к реализации, не сейчас.
- **Fund Details / Holdings / Fund Chart / My Investments** — визуально подтверждают, что уже
  решённая модель NAV/units/holdings/activity укладывается в такой набор экранов без противоречий.
- **Verified badge на карточке фонда** — возможная лёгкая альтернатива полной pre-approval очереди
  (которую убрали из v1): бейдж после постфактум-модерации вместо блокировки публикации.

**Противоречия с уже принятыми решениями, найденные в мокапах (требуют подтверждения):**

- Bottom-nav на мокапах (Dashboard/Portfolio/Funds/Activity/Profile) — отдельная навигация под этот

## Открытые вопросы / решения, блокирующие математику

Отранжировано по тому, насколько сильно решение меняет всё остальное.

1. **Источник цен: реальный рынок или синтетический мир?**
   Текст одновременно говорит «у AAPL/MSFT одна реальная цена» (= текущий live-фид Finnhub/Yahoo,
   который уже использует Portfolio) и «Market Phase BEAR, Day 142» (= синтетический движок как в
   Stress Test, с собственной фазой рынка, которая должна тикать *постоянно*, а не только во время
   сессии теста). Это два принципиально разных движка:
   - **Live-данные**: дёшево, переиспользуем существующую инфраструктуру цен, но тогда «мировая
     симуляция» — это просто реальный рынок, и весь пункт про market phase/day counter не нужен.
   - **Синтетический персистентный мир**: нужен постоянно работающий серверный процесс (не по запросу,
     а тикающий в реальном времени 24/7 на Hetzner), который двигает цены даже когда никто не открыл
     приложение — иначе NAV фондов не будет меняться между сессиями. Это отдельный большой кусок
     инфраструктуры, которого сейчас нет.
   Нужно выбрать один вариант до расчёта остальной математики.

2. **Management ownership vs management fee — это одно и то же или два разных начисления?**
   Если оба одновременно — нужно явно расписать, как fee минтит/списывает units (размывает ли она
   остальных держателей) и не задваивается ли с «стартовым пакетом» управляющего.

3. **Валюта фонда — виртуальная или реальная?**
   Ты сам называешь это «виртуальной биржей», но Premium (создание фонда) — это уже реальные деньги
   пользователя, привязанные к виртуальному AUM с рейтингами и соревнованием. Это близко к схеме
   «плати за доступ к инвестиционной игре с виртуальным capital» — не проблема сама по себе, но стоит
   явно решить формулировки/дисклеймеры, учитывая, что у приложения уже есть чувствительность к этому
   (Privacy/Terms drafts, история с disclaimer-ссылками).

4. **Ликвидность при Sell.** У виртуального фонда нет реального ограничения «нет кэша — нечем платить»,
   но если хочется реализма/риска — нужно явно решить: NAV считается mark-to-market мгновенно (продажа
   всегда возможна по текущему NAV), или движок симулирует, что фонд обязан распродать активы (со
   slippage/задержкой), если cash-buffer исчерпан.

5. **Откуда берётся Starting Capital.** Это собственные виртуальные деньги создателя фонда (снимаются
   с его личного баланса/портфеля) или движок просто выдаёт €50 000 «из воздуха» при создании фонда?
   Второй вариант — эмиссия денег в системе при каждом новом фонде, экономику надо на это закладывать.

6. **Governance/voting в Management Room.** Кворум, вес голоса (поровну или по % ownership), что
   происходит при разногласии/таймауте, нужен ли порог, ниже которого решение не требует голосования.

7. **Anti-abuse.** Wash trading (менеджер накачивает свой же фонд с альтов), накрутка Trending,
   «rug-pull»-паттерн (собрать AUM → выкачать fee → бросить фонд). Раз в системе есть fee/ranking —
   нужны хотя бы базовые правила защиты, иначе первый же топ-фонд будет фермой.

8. **Пересечение с существующими Portfolio/Stress Test тирами.** Сейчас у пользователя уже есть слоты
   и лимиты ($7k/$10k Portfolio, $7k/$15k Stress Test — см. память). Инвестиции в фонды — это третий
   параллельный «карман» денег или они завязаны на существующий баланс/слоты?

9. **⚠️ ВАЖНО при реализации — потолок в $1,000,000 на `user_data` (2026-09-05).** В рамках
   пре-релизного аудита в `docs/supabase_migration.sql` добавлена Migration 012 — триггер на таблице
   `user_data`, который **отклоняет запись**, если `portfolios[].startingBalance`,
   `stress_test_sessions[].startingCash` или `stress_test_verdicts[].startingCash` превышает
   $1,000,000 (анти-чит защита от подделки баланса клиентом напрямую через Supabase REST API — см.
   комментарий в самом файле миграции).
   Сейчас это ETF-фичу не задевает: стартовый капитал фонда (150K на старте, было 500K в более ранней
   версии этого документа) и рост AUM от притока юзеров/ботов — это агрегатные данные фонда,
   которые по плану живут в отдельных новых таблицах (`Fund`, `FundHolding`, `FundTransaction`,
   `FundNavSnapshot`), не в `user_data`. Инвесторский «карман» обычного пользователя (сколько лично
   он вложил в чужой фонд) по плану — третий изолированный пул в духе тиров Portfolio/Stress Test
   ($7-15k), тоже далеко от потолка.
   **Если при реализации что-то из фонда всё же ляжет новой колонкой в `user_data`** (как раньше
   `stress_test_sessions` добавили через Migration 004) — обязательно свериться с Migration 012:

   вдруг перестанет сохраняться без явной причины, первым делом проверить именно это.
